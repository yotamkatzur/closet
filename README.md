# ארון — Closet

בורסת שמלות ערב יד־שנייה, מסוננת לפי הגוף שלך. עברית, RTL, ₪, ישראל בלבד.
גרסת פיילוט ל~40 משתמשות.

זה ה־README הפרקטי. אם משהו לא עובד — כל שלב כאן אמור לרוץ בהעתקה של פקודה אחת.

---

## הרצה מקומית (5 דקות, בלי שום שירות חיצוני)

צריך **Node 20+** מותקן. זהו.

```bash
npm install          # התקנת חבילות
cp .env.local.example .env.local   # קובץ הגדרות — אפשר להשאיר כמו שהוא
npm run seed         # ממלא 38 שמלות דמו + 12 משתמשות (כולל חשבון ניהול)
npm run dev          # מריץ את האתר
```

פותחים בדפדפן: **http://localhost:3000**

### איך מתחברים

האפליקציה שולחת קוד ב־SMS. בפיילוט אין ספק SMS — **הקוד מודפס בטרמינל** שבו רץ
`npm run dev`. מחפשים שורה כמו:

```
┌──────────────────────────────────────────┐
│  OTP for +972500000000: 123456           │
└──────────────────────────────────────────┘
```

* **חשבון ניהול (המייסדת):** טלפון `050-0000000` → מזינים את הקוד מהטרמינל → נכנסים
  ל־`/admin`.
* **חשבונות מוכרות לדמו:** `050-0000501`, `050-0000502` … עד `050-0000511`.
* **משתמשת חדשה:** פשוט נכנסים לפיד, לוחצים על שמלה, וממלאים גובה + מידה.

### פקודות שימושיות

| פקודה | מה היא עושה |
|---|---|
| `npm run dev` | מריץ את האתר במצב פיתוח |
| `npm run seed` | ממלא נתוני דמו (לא מוחק קיימים) |
| `npm run db:reset` | **מוחק הכל** וממלא נתוני דמו מחדש |
| `npm test` | מריץ את הבדיקות (אלגוריתם ההתאמה + מכונת המצבים של העסקה) |
| `npm run build` | בונה גרסת פרודקשן |

הנתונים המקומיים נשמרים בקובץ `.data/db.json` (טקסט קריא) והתמונות ב־`public/uploads/`.
אפשר לפתוח את `.data/db.json` ולראות בדיוק מה קורה.

## מה בפנים

* **פיד** (`/`) — שמלות מסודרות לפי כמה הגוף של המוכרת דומה לשלך. כל כרטיס מקבל
  משפט כן: "גבוהה ממך ב־4 ס"מ · בדרך כלל מידה אחת מעליך". יש מתג "כל המידות"
  שמכבה את הסינון. **אין שום פילטר מידה קשיח בשום מקום** — רק סדר ותוויות.
* **דף שמלה** (`/item/[id]`) — בלוק ההתאמה הבולט (הגובה והמידה שלה מול שלך), מה
  המוכרת אומרת על השמלה הזו, ומדיניות ההחזרה של 48 שעות לפני הקנייה.
* **ארון** (`/u/[id]`) — פרופיל מוכרת: כרטיס גוף, שמלות למכירה, שמלות שנמכרו
  (מסומנות "נמכר", לא נמחקות), עוקבות.
* **מכירה** (`/sell`) — צילום → **מילוי אוטומטי מהתמונה** (צבע, אורך, מחשוף,
  אירועים) → תיקון ידני → מחיר → פרסום. יעד: פחות מדקה.
* **בקשות קנייה** (`/requests`) — המוכרת רואה מי רוצה את השמלה שלה, את כרטיס הגוף
  של הקונה ואת ההודעה, ומאשרת / דוחה / חוסמת.
* **עסקאות** (`/deals`) — לשוניות "קניתי" / "מכרתי" + בקשות פתוחות. אחרי אישור:
  **כרטיס תיאום** עם מספרי טלפון, כפתור וואטסאפ, סכום, קוד תשלום (`CL-####`),
  כפתורי העתקה, וספירה־לאחור.
* **חיפוש** (`/search`) — פילטרים מובנים (לא צ'אט־בוט).
* **ניהול** (`/admin`) — חדר הבקרה: עסקאות שדורשות טיפול (מחלוקות, אי־התאמות
  תשלום), בקשות, פריטים, השעיית/חסימת משתמשות, יומן אירועים גולמי.
* **מדדים** (`/admin/kpi`) — לוח ה־KPI של הפיילוט מול היעדים.

* **צ'אט** (`/chat/[txId]`) — צ'אט פנימי לכל עסקה, זמין אחרי אישור הבקשה. רץ לצד
  וואטסאפ. Polling כל 4 שניות (אין websockets בפיילוט).

### כסף — ביט P2P מתואם, בלי נאמנות (מצב פיילוט)

* **האפליקציה לא מעבירה כסף, לא מחזיקה כסף ולא שומרת פרטי תשלום.** היא מפגישה בין
  שתי הנשים, נותנת סכום מדויק וקוד ייחוס, ורושמת רק ששתיהן דיווחו שהעסקה בוצעה.
  הכסף עובר בביט ישירות ביניהן. שכבת `PaymentRecorder` ב־`src/lib/providers/`
  היא no-op בכוונה — אין קוד שיכול להפוך את Closet למעביר כספים.
* תמונת פרופיל: כל משתמשת מעלה/מחליפה מהארון שלה (`AvatarUpload`).
* אין עוסק, אין סליקה, אין מע"מ. את (יַם) נשארת אדם פרטי שמריץ פרויקט בין חברות.
* **תשלום בזמן המסירה** הוא ברירת המחדל — הקונה רואה את השמלה ואז משלמת.
* שני הצדדים מאשרים תשלום בנפרד. כששניהם אישרו — העסקה נסגרת וחלון ההחזרה של
  48 שעות מתחיל. אם רק צד אחד אישר ואחרי 72 שעות אין התאמה — סומן לבדיקה שלך.
* **48 שעות להחזרה מרגע המסירה.** אין נאמנות, אז ההחזר הכספי מתבצע ישירות בין
  שתי הנשים — ואת הערבה בפיילוט. ראי `closet-payment-contact-spec.md`.
* עמלת 8% נרשמת בעסקה לצורכי v2 אבל **לא נגבית** בפיילוט. ארנק פנימי → v2 עם נאמנות.
* משלוחים: ברירת המחדל "איסוף עצמי". שמלה יקרה שנשלחת לזרה מקבלת התראה "מומלץ להיפגש".

### חשיפת מספר טלפון

מספרים נחשפים **רק** אחרי שהמוכרת מאשרת בקשה ספציפית, **רק** לאותה קונה, **רק**
לאותה עסקה. שני הצדדים מקבלים הודעה ברגע החשיפה. כל חשיפה נרשמת ב־`analytics_events`
כאירוע `phone_revealed`. מוכרת יכולה לדחות ולחסום בלי לתת סיבה, וזה לא שולח הודעה
לצד השני.

### אנליטיקה (עצמית בלבד)

* אין Mixpanel / GA / Meta Pixel. הכל נכנס ל־`analytics_events` ו־`feed_impressions`
  שבמסד שלך. הטבלאות האלה **קריאות לניהול בלבד** ברמת ה־RLS.
* **מידות גוף ותמונות לא נכתבות לאנליטיקה אף פעם** — רק `user_id` וערכים מקובצים
  (גובה הופך ל־`163-167`). יש סקראבר ב־`src/lib/analytics.ts` שמנקה זאת דיפנסיבית.
* הניסוי המרכזי — CTR לפי טיר בחלון הכרונולוגי — נמדד ב־`feed_impressions` עם
  `tier` / `match_score` / `position` / `feed_mode` שנשמרים **בזמן הרינדור**.
  **אל תדליקי מצב דירוג במהלך הפיילוט** גם אם המלאי חוצה 300 — זה הורס את המדידה.
* דיווח על מכירה מחוץ לאתר: כפתור "נמכר" על כל שמלה שלך → "נמכרה במקום אחר" +
  ערוץ (פייסבוק / וואטסאפ / …) + מחיר. זה ה־floor, לא מדידה — מסומן ככזה בלוח.
* צילום מדד שבועי: כפתור בראש `/admin/kpi`, או cron `/api/cron/kpi-snapshot`.

### Cron

צריך שמשהו "ידפוק בדלת" — פקיעת בקשות (24ש׳), פקיעת הזמנות (48ש׳), סגירת חלון
החזרה, זיהוי אי־התאמות תשלום, ותזכורות SMS:

* **מקומית:** בטרמינל נפרד —
  `while true; do curl -s localhost:3000/api/cron/sweep; sleep 300; done`
* **בפרודקשן (Vercel):** מוגדר ב־`vercel.json` — sweep כל 15 דקות, snapshot יום שני.
* **ידנית:** כפתור "הרץ בדיקת פקיעת חלונות ותזכורות" בראש `/admin`.

בפיילוט אין ספק SMS — הודעות ה־SMS **מודפסות בקונסולת השרת** עם הקידומת `[SMS → …]`.

## פריסה לאוויר (Railway + Twilio)

**ראי `DEPLOY.md`** — מדריך צעד־אחר־צעד: GitHub → Railway (עם persistent volume)
→ Twilio לקודי SMS אמיתיים → דומיין → cron → כניסה ראשונה כ-admin. הקוד כבר מוכן
(`Dockerfile`, `railway.json`, `src/lib/sms.ts`); צריך רק להקים חשבונות ולהדביק
מפתחות. עלות ~$5/חודש.

`ADMIN_PHONES` הופך את מספר הטלפון שלך ל-admin בכניסה הראשונה — אין צורך ב-seed
בפרודקשן, מעלים שמלות אמיתיות דרך האפליקציה.

## מעבר ל-Supabase (מאוחר יותר, אם זה גדל)

הפיילוט רץ על אחסון קובץ JSON. כשזה מתחיל לגדול:

1. **מסד נתונים — Supabase.** פותחים פרויקט, מריצים את כל הקבצים ב־
   `supabase/migrations/` לפי הסדר (`0001` … `0005`, כולל Row Level Security
   ואת שינויי מודל התשלום). ממלאים ב־`.env.local`:
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
   ומשנים `DATA_DRIVER=supabase`.
   > נשאר לממש קובץ אחד: `src/lib/db/supabase.ts` שמממש את אותו ממשק כמו
   > `src/lib/db/repo.ts`. כל שאר הקוד כבר לא יודע מאיפה מגיעים הנתונים.
2. **תמונות — Supabase Storage** עם signed URLs ובאקט פרטי (ראו `src/lib/media.ts`).
3. **SMS אמיתי** — מחליפים את `smsLog()` ב־`src/lib/tx/engine.ts` וב־
   `src/lib/actions/auth.ts` (`AUTH_DRIVER=sms`).
4. **נאמנות אמיתית (v2)** — רק אחרי שהפיילוט עובר את השערים. עוסק + חוזה עם Grow
   / PayPlus / Tranzila + `BitGatewayPaymentProvider` שמממש את `PaymentProvider`
   שב־`src/lib/providers/payment.ts`. **התייעצי עם רו"ח לפני שבונים** — יַם הופכת
   ל־merchant of record. ראו `closet-payment-contact-spec.md` §9.
5. **מילוי אוטומטי אמיתי** — `AI_DRIVER=claude` + `ANTHROPIC_API_KEY`.
6. **דירוג — כשחוצים 300 שמלות זמינות** הפיד עובר מסדר כרונולוגי לדירוג לפי ציון
   התאמה, אוטומטית. הסף: `MATCH_RANKING_MIN_INVENTORY`.

## מבנה הקוד (לרפרנס)

```
src/lib/match.ts            אלגוריתם ההתאמה — פונקציה טהורה, נבדקת ביחידות
src/lib/txStateMachine.ts   מכונת המצבים של העסקה — טהורה, נבדקת ביחידות
src/lib/tx/engine.ts        בקשות קנייה + מעברי מצב + sweep (SMS, פקיעות, אי־התאמות)
src/lib/feed.ts             הרכבת הפיד (כללי הסינון והדירוג)
src/lib/analytics.ts        track() צד־שרת + סקראבר מידות גוף + קיבוץ גובה
src/lib/analytics/client.ts track/flush צד־לקוח (בופר, beacon, session_id)
src/lib/kpi.ts              חישוב כל ה־KPI מ־§7 של ספק האנליטיקה
src/lib/db/repo.ts          שכבת הנתונים — כל שאר הקוד מייבא רק מכאן
src/lib/providers/          ממשקי תשלום / AI + מימוש ידני/סטאב לפיילוט
src/data/he.ts              כל הטקסט בעברית. אין מחרוזות קשיחות בקומפוננטות.
supabase/migrations/        סכימת SQL מלאה + RLS (0001…0005)
```

בדיקות: `npm test` (31) — מכסה את `matchScore`, מיפוי המידות לסדר (כולל S-M / M-L),
וכל מעבר מצב בעסקה: אישור תשלום כפול → מסירה, מסלול ההחזרה, ופקיעת ההזמנה.
